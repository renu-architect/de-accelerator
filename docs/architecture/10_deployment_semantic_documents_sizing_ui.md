# 10 — Deployment, Orchestration Providers, Semantic, Documents, Sizing, UI-readiness (Rev 1)

## 1. Deployment topologies (Terraform)
Default and options are a single Terraform variable `topology`, so cost/isolation trade-offs are a client choice, not a code fork.

| Topology | Workspaces | Catalogs | When | Trade-off |
|---|---|---|---|---|
| **ISOLATED (default)** | DEV, QA, PROD separate | `<client>_dev/_qa/_prod` | regulated / default | highest isolation, highest fixed cost |
| NONPROD_SHARED | DEV+QA share one; PROD separate | per-env catalogs, per-env SPs | cost-sensitive | non-prod blast radius shared; strict UC grants required |
| SINGLE_WORKSPACE | one for all | per-env catalogs | small/PoC | weakest isolation; PROD secrets scopes separated; not recommended for PROD of regulated clients |
Cost options (variables): serverless vs classic job clusters, cluster profiles (S/M/L), spot ratio, SQL warehouse size/auto-stop, predictive optimization, log retention, GRS vs ZRS storage.

**Terraform structure** (in `deployment/iac/`): modules `network`, `storage_adls`, `keyvault`, `databricks_workspace`, `unity_catalog` (metastore assignment, catalogs, schemas, external locations, storage credentials via Access Connector/MI), `identities` (SPs/MI, groups), `grants`, `cluster_policies`, `secret_scopes` (KV-backed), `monitoring` (Log Analytics, budgets), `dr`. Remote state in a geo-replicated storage account with locking; one state per env; `terraform plan` required in CI, apply via approved pipeline; policy checks (tfsec/checkov). Secrets never in tfvars (KV references).
Databricks workload deployment (jobs, wheel install) via **Databricks Asset Bundles** (workflow definitions generated by the orchestration provider).

## 2. Orchestration provider interface (extensible; MVP = Databricks Workflows)
```
OrchestrationProvider
  capabilities() -> {parallel_fanout, repair_run, cron, dependencies, max_tasks}
  render_deployment(plan: ExecutionPlan) -> DeploymentArtifacts   # e.g. DAB bundle files
  deploy(artifacts, env) / undeploy
  submit_run(execution_id, params) -> ProviderRunRef
  get_status(ref) / cancel(ref) / repair(ref, tasks)   # repair optional by capability
  schedule(execution_id, cron/timezone) / unschedule
  emit_alert_route(config)
```
The framework owns the **plan**, dependency graph, retry/restart *semantics* and state tables; the provider only translates to/runs on a scheduler. `DatabricksWorkflowsProvider` is the only MVP implementation. Future: `AdfProvider`, `AirflowProvider`, `AzureDevOpsSchedulerProvider`. A provider conformance test-suite is part of the interface contract. `cfg_execution.provider` + `cfg_orchestration_provider` (options JSON) select the provider.

## 3. Semantic layer: outputs and Power BI validation
Generators (all from `cfg_semantic_*`): (a) **Databricks SQL views**, (b) **UC metric views** (YAML-spec), (c) **Power BI TMDL / PBIP**.
**Validation & deployment tests (mandatory for TMDL generator to be COMPLETE):**
| Test tier | What | Needs |
|---|---|---|
| T1 static | TMDL parse/compile (Tabular Editor CLI / TOM), naming/format rules, Best-Practice-Analyzer rules, relationship integrity vs Gold keys | CI agent |
| T2 SQL parity | metric-view/SQL-view results vs independent PySpark calc on fixture data | Databricks SQL warehouse (DEV) |
| T3 **deployment** | deploy TMDL to an ephemeral/test Power BI (Fabric) workspace via Fabric/Power BI REST API with SP; bind to Databricks SQL warehouse via secret-held credentials | Fabric/Premium capacity, tenant setting "service principals can use APIs", SP in workspace |
| T4 refresh + **DAX validation** | trigger refresh; run `EVALUATE` queries (row counts, measure values vs T2 results, relationship cross-filter behavior, RLS role tests if configured) via XMLA/`executeQueries` | same |
| T5 cleanup/idempotency | redeploy is idempotent; ephemeral workspace torn down | same |
**Dependency & honesty:** T3–T5 cannot run without a client-or-provider Power BI/Fabric capacity and tenant admin enablement; until available, TMDL status can only reach `IMPLEMENTED` (T1–T2 passing), not `COMPLETE`. Never auto-publish to PROD workspaces; PROD deploy via client BI release approval. Complex DAX beyond approved templates = extension.

## 4. Document (unstructured) processing in the overall architecture
- Source kind `document` sits beside structured and semi-structured in `cfg_source/cfg_object`; same onboarding, batch manifest, file-tracking, audit and lineage mechanisms. Raw originals are preserved byte-for-byte in a raw Volume/container (content-hash path; immutable).
- **Interfaces:** `DocumentExtractor` and `OcrProvider` (`analyze(doc_ref, options) -> pages[text, layout, tables, confidence]`), `Classifier`, `EmbeddingProvider`, `VectorIndexer` — all replaceable.
- **Default OCR provider: Azure AI Document Intelligence** (`AzureDocumentIntelligenceProvider`), accessed via Managed Identity/KV-held key, private endpoint, with throttling/retry, cost budget cap per run, and provider selected by `cfg_doc_pipeline.ocr_provider`. Fallback providers (pdfplumber/python-docx/Tesseract) are optional implementations of the same interface.
- Outputs: `doc_registry` (doc id, hash, type, source path, pages, status), `doc_page` (page-level traceability: page no., text, confidence, bbox ref), `doc_extraction` (structured fields/tables), `doc_classification`.
- **Tiering:** M1 — metadata DDL only (`cfg_doc_pipeline`, doc source type validated). V1 — landing/preservation, extraction via Azure DI, page traceability, classification. V2 — embeddings, vector search, RAG integration. Erasure (doc 11) applies to extracted content and vectors.

## 5. Sizing — design targets (NOT guarantees)
Initial design targets per client: **500–5,000 objects** and **up to 10 TB** total data. These shape defaults (Workflows grouping, metadata read caching, snapshot size, file sizing) and **must be validated by performance & scalability tests** before any claim is made to a client.
| Test (planned) | Purpose | Reported metric |
|---|---|---|
| Metadata scale (M1 unit/benchmark): 500/2,500/5,000 objects × ~50 cols | validate time, snapshot size/hash time, reader latency, loader duration | seconds, MB |
| Planner/DAG scale (M4) | plan + task generation at 5,000 objects incl. grouping vs provider task limits | plan time, tasks |
| Ingestion throughput tiers (M2/M3) | 100 GB / 1 TB / 10 TB synthetic | GB/h, cost, small-file ratio |
| Concurrency/contention | parallel MERGE to different/same targets | conflicts/retries |
| Audit volume | log-table growth & query latency at 5,000 objects × daily runs | rows/day, dashboard latency |
Acceptance thresholds will be defined with you before M6; results are published as measured, with environment details.

## 6. Metadata UI: outside MVP, but UI-ready
- MVP: Git + PR approval + CI + release pipeline (doc 09 §1).
- Interfaces designed now (implemented in M1 as library API; no UI): `MetadataService` — `validate(draft)`, `diff(a,b)`, `list/get` entities, `propose_change(draft) → PR` (writes **to Git**, never directly to Delta), `release_status`, `lineage_of_config`. Versioned JSON-Schemas and stable error codes are the UI contract; pack format is machine-friendly.
- Future UI = a client of `MetadataService` that creates branches/PRs; approvals and promotion stay in Git/CI. Direct Delta editing remains disallowed (ADR-0002/0016).
